# Asset provenance

Where the files in this directory came from, and what is known about their
licensing. Written 2026-07-27, when the first asset with a traceable origin was
added — everything above that line arrived with the 2016 tree and its provenance
is genuinely unknown rather than merely unrecorded.

**Why this file exists.** Three distribution channels are planned, one of which is
Steam ([planning/2026-07-25-packaging-distribution](../planning/2026-07-25-packaging-distribution/)).
An asset of unknown origin in a store build is an actual problem rather than a
theoretical one, and the way that happens is not malice — it is that nobody wrote
the origin down while it was still cheap to. So: **anything added here gets a row,
including the ones where the honest answer is "unknown".**

### Sunny Land — `sunny-land/foxy/`, `foxy.png`, `foxy.xml`

Foxy's 36 frames across 12 animations, uniform 33×32 as authored. The licence
PDF shipped with the pack states it plainly:

> "All assets included in this package are licensed under the Creative Commons
> Zero (CC0) license, which means you can use them freely in any project,
> whether personal or commercial, without the need for attribution. There are no
> restrictions on use, modification, or redistribution of these assets."

**So this is shippable**, which the glyph sheet below is not. Attribution is not
required; the row above records the author anyway, because knowing where a file
came from is the point of this document and is a separate question from what the
licence compels.

Only the frame PNGs are committed. The pack as purchased is 5.9 MB of PSD and
`.ase` sources, preview GIFs and PDFs that nothing reads, and it is gitignored
rather than carried — a size decision, not a legal one.

`foxy.png` and `foxy.xml` are **generated, and regenerating them is expected to
produce identical bytes**:

```sh
tools/.venv/bin/python tools/pack_atlas.py data/sunny-land/foxy \
    --name foxy --out data
```

The packer trims transparent margins, so the sheet is 140×270 rather than the
198×384 the pack's own `atlas.png` uses, and every frame carries Sparrow trim
attributes. That is deliberate beyond the size saving: before this, nothing in
`data/` exercised the trim path, and a trim offset applied with the wrong sign
draws a sprite a few pixels out of place rather than failing. The tool's verify
pass rebuilds each frame from the atlas and compares it to its source, which is
what makes that convention checked rather than asserted. It runs by default;
`--no-verify` is what turns it off.

`foxy.anim.xml` is a different kind of file: generated *once* as a starting
point and edited by hand after, since Sparrow carries no timing and the frame
rates are a judgement call rather than something derivable. A regenerate merges
into it rather than overwriting, so the tuning survives. It contains no art and
is the project's own.

### Sunny Land — `sunny-land/critters/`, `critters.png`, `critters.xml`

The same pack and the same CC0 grant quoted above, so the licence question is
settled by that section rather than restated here. 38 frames across 8 animations,
covering the frog, opossum, eagle and the four items.

The destination names are not the source names, and the mapping is worth recording
because three of them are renames and one is invented outright:

| Destination | Source, under `Assets/` | Frames | Authored size |
|---|---|---|---|
| `frog-idle` | `Characters/frog/Sprites/idle` | 4 | 35×32 |
| `frog-jump` | `Characters/frog/Sprites/jump` | 2 | 35×32 |
| `opossum-walk` | `Characters/Opossum/opossum` | 6 | 36×28 |
| `eagle-swoop` | `Characters/eagle/Sprites/attack` | 4 | 40×41 |
| `cherry` | `Misc/Sunnyland items/Sprites/cherry` | 7 | 21×21 |
| `gem` | `Misc/Sunnyland items/Sprites/gem` | 5 | 15×13 |
| `puff` | `Misc/Sunnyland FX/Sprites/enemy-death` | 6 | 40×41 |
| `sparkle` | `Misc/Sunnyland FX/Sprites/item-feedback` | 4 | 32×32 |

`enemy-death` → `puff`, `attack` → `swoop` and `item-feedback` → `sparkle` are
renames into this game's vocabulary; `opossum-walk` has no source directory to take
a name from at all, since the opossum's six frames sit flat in `Opossum/opossum/`.
The prefixing rule is decision 15 in
[planning/2026-08-10-game-layer-and-demo](../planning/2026-08-10-game-layer-and-demo/README.md).
The frames are otherwise byte-identical copies, renumbered from the pack's 1-based
unpadded names to the `NNN.png` the packer's verify pass expects.

As with Foxy, only the frame PNGs are committed and the pack as purchased is
gitignored.

`critters.png` and `critters.xml` are **generated, and regenerating them produces
identical bytes** — checked:

```sh
tools/.venv/bin/python tools/pack_atlas.py data/sunny-land/critters \
    --name critters --out data
```

The trimmed sheet is 190×214, comfortably inside the Miyoo Mini's 640×480 texture
cap. `critters.anim.xml` is hand-tuned after seeding and merges on a regenerate,
exactly as `foxy.anim.xml` does.

**One thing to know about this art specifically.** It carries
`(255, 255, 255, 0)` in its transparent regions where Foxy's carries
`(0, 0, 0, 0)` — authoring tools differ on what to leave in the matte, and
nothing observable distinguishes the two. The verify pass accounts for that: it
compares alpha exactly and ignores colour beneath a fully transparent pixel, so
all 38 frames rebuild clean. It compared all four channels until 2026-09-08,
which made this art report as 38 mismatches while being correct (D32 in
[the defect inventory](../planning/2026-07-25-cxx17-modernization/defects.md)).
Anything packed from a third source needs no special handling on this account.

### `sunnyland.tmx` — generated, not authored in Tiled

The snapshot asks for a tilemap fixture authored in Tiled. Tiled is a GUI and
there is no way to drive it headlessly, so `tools/make_tilemap.py` writes an
equivalent file instead: the same format and attribute set, CSV layer data, an
external `.tsx`, an object layer. It opens and edits in Tiled, and regenerating
is deterministic.

**This is worth stating plainly rather than letting the file imply otherwise.**
A `tiledversion` attribute in a document no copy of Tiled has ever touched is
exactly the sort of detail that gets believed later.

The map is 64×36 tiles of 16×16, larger than any target panel so that a renderer
has to cull. Its backdrop layer covers **every** cell, which is deliberate: it
makes the fixture the worst case for fill rate rather than a flattering one, and
it is why the numbers in
[target-validation/results.md](../planning/2026-07-25-target-validation/results.md)
mean something.

### `orchard.tmx` — also generated, and the opposite map

Tiled is no more available for this one, so `tools/make_orchard_level.py` writes
it the same way and the same caveat applies: no copy of Tiled has touched the
file despite the `tiledversion` attribute it carries.

It borrows the fixture's tileset — the same `tileset.png` through the same
external `sunnyland.tsx` — so the map itself adds no licence question; the cloud
tiles its generator draws into that sheet are covered below. What it does not
borrow is the fixture's purpose. `sunnyland.tmx` is the worst case
for fill rate; this is decision 4 of
[the game-layer snapshot](../planning/2026-08-10-game-layer-and-demo/), which
authors *against* overdraw: no backdrop layer at all, sky is `Context::clear()`,
two visible tile layers and an invisible `collision` layer. 96×40 tiles of 16×16
is 1536×640 pixels, larger than the 640×480 Miyoo panel on both axes so that the
camera scrolls and clamps on each.

It also adds the only art in `tileset.png` that did not come from the pack. The
sheet has no cloud in it, and rock rubble does not recolour into one — a rock's
internal detail is random and high-contrast, a cloud's shading follows its
silhouette, and no palette swap changes that. So `--bake-tiles` *draws* fourteen
cloud tiles and writes them into ids 541–554, which were already in the sheet
and fully transparent, referenced by neither map.

Writing into existing empty slots rather than appending a row is deliberate:
`tests/test_tmx.cc` asserts `tilecount == 575` against a 400×368 image, and
growing the sheet would turn it red for nothing. Every pre-existing gid is
untouched.

Licence-wise this splits the file. The pack's tiles stay **CC0 1.0** by Luis
Zuno; the fourteen drawn tiles are the project's own work, generated from
`CLOUD_SHAPES` in `tools/make_orchard_level.py` — circles, a flat bottom edge
and two tones, with no pack pixels involved. CC0 imposes nothing either way, so
this is a statement of fact rather than a licence obligation.

Two maps with opposite jobs, which is why there are two generators and not a
flag. The generator refuses to write a map whose own tables disagree — a
platform buried in the hillside, a pickup perched where there is no platform, a
spawn outside the level — because `game::Level` would load all three happily.

### `jetpackdude.xml`

Authored for this project in 2016, so its licence is not an open question. Its
sheet, `JetPackDude.png`, is not in the repository and the original art has not
been located — the atlas is orphaned and cannot be drawn.

It is kept anyway, as `test_sparrow`'s fixture for the *untrimmed* path: eight
frames of `reddude.NNN` at 24×34 with no `frame*` attributes, which is a real
exporter's output of a shape `foxy.xml` no longer contains now that every frame
in it is trimmed. Parsing needs no image. Anything that needs to *draw* uses
`foxy.xml`.

### `emerald-droplets.xm`

The first module in this directory with an attributable licence, which is the
point of it — the three inherited `.mod` files below cannot be given one.
Attribution is to **malmen**, and the licence requires it.

The credit is carried the way tracker music has always carried it, in the
instrument names, read down the list:

> emerald droplets · by malmen of · satanic kids · enterprise ·
> my first 2010 release · :)

Inspected rather than taken on the filename, since a module's metadata is where
its authorship actually lives: Fasttracker II format, written by MilkyTracker,
XM version 1.04. 24 channels, 46 patterns, 46 orders, tempo 4 at 161 BPM,
17 instruments across 19 samples, 174 KB.

Most of those samples are 30–60 byte single-cycle waveforms rather than recorded
audio, which is why a 24-channel module of this length is that small. Five are
longer and carry the filenames of their source material — `VEE CLOSED HIHAT
87.wa`, `VEE Bassdrum 156.wav`, `VEE SNARE 145.wav`, `CF DEEPHSE CRSH 07.wav`
and `Noise Type 1 (Long)` — recorded here because sample-level origin is not
something a module-level licence speaks to, and this document exists so that the
question is asked once per file rather than never.

**No codec cost.** `WREEL_AUDIO_CODECS=minimal` is already WAV + tracker
(MOD/XM/IT), so XM adds nothing to any target. What it does add is mixing load:
24 channels where every module previously in this tree is a 4-channel `M.K.`,
against a handheld mixer profile of 22050 Hz / 2048 samples / 8 voices on two
Cortex-A7 cores. Tracked as a risk in
[planning/2026-08-10-game-layer-and-demo](../planning/2026-08-10-game-layer-and-demo/).
On 2026-10-06 it played on a Miyoo Mini under `orchard`, which held 59.7 fps at
the default frame cap ([results.md](../planning/2026-07-25-target-validation/results.md),
orchard's first device run). 2026-10-16: confirmed audible by the user on the
device (sound effects and module playback in orchard and coppers); not logged.
The mixer's own cost is still not isolated: no `--mute` run has been made to
compare against.

### `glyphs-16x16.png`

A 320×48 sheet: 60 cells of 16×16, twenty columns, three rows, ASCII 32–91
(uppercase, digits, basic punctuation; `*` is drawn as a heart). Two tones with no
alpha channel, so it is read as a 1-bit mask and recoloured in code rather than
colour-keyed — which is what lets the palette switch recolour the scroller text as
well as the bars.

Renamed from the upstream `5611500775_36717acd08_o.png`, which is a Flickr-style
identifier carrying no information; the original name is recorded above so the file
stays traceable.

**The licence is unknown and this is not shippable as it stands.** That collection
has no LICENSE file, and its README states plainly:

> "No metadata and I do not claim rights to any of these works, I just thought
> after finding a few of these sites had died that I should make it available."
>
> "I don't remember where much of this collection came from."

So it is a demoscene-archive rip whose author cannot be identified from it. Fine
for developing and measuring against, which is what it is doing now. **Before any
shipped build**, either identify the author and obtain terms, or substitute a
license-clear pixel font — a CC0 or OFL sheet, or one authored for the project.
`coppers::GlyphSheet` takes a grid geometry and a surface, so swapping the file is
a data change and not a code change, provided it is done before something depends
on this specific grid.

It is already in the `coppers` bundle (`coppers/CMakeLists.txt`,
`WREEL_BUNDLE_ASSETS`), so any Onion package built from this tree carries it.
